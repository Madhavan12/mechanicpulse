# MechanicPulse — Test Cases

One section per feature. Each section lists test cases derived from the actual requirements (CLAUDE.md, product-decisions.md, data-model.md, the frontend spec) — not reverse-engineered from the code — then says whether each case is covered by an automated test, and where.

**Rule (see README ground rules): this doc must be updated in the same PR as the development it describes** — new feature, new case; changed behavior, updated case; case now automated, updated status.

Format per feature:

```
## Feature: <name>

| # | Requirement source | Case | Expected result | Automated? |
|---|---|---|---|---|
```

`Automated?` is one of:
- ✅ `path/to/file.test.ts` — "test name" — covered by an automated test
- 🔸 Manual only — needs a human/click-through check, not yet automated (and says why, if it's a real blocker like needing a browser or a real Postgres)
- ⬜ Not yet covered — a known gap

## Feature: Active Job (`/jobs/[id]` + findings, photos, send)

Built on `feature/view-job`: view a job, add/edit/delete findings, Estimate card (cases 1–8, 18–20), then photos and Send Report (cases 9–17, 21–26) — kept in the same PR because they're part of the same page. Written before the code from `docs/mechanic-pulse-frontend-spec.md` (Active Job) and `docs/data-model.md`.

Verified 2026-11-02: the e2e tests in `apps/web/e2e/active-job.spec.ts` and `apps/web/e2e/photos-and-send.spec.ts` pass in mobile Chrome and mobile Safari against a real Postgres 16 (full suite: 146 passed, 2 skipped), with 218 API unit tests (re-run 2026-11-03 after the PR #45 review fixes: same 146 passed, 2 skipped; 218 API tests).

**What the photo e2e tests do and don't prove.** They run the way CI does — throwaway AWS credentials, no real bucket. The browser's PUT to S3 is stubbed, and the API's server-side check of the object in S3 then genuinely fails, so they exercise the **failure** path end to end (Failed/Retry, `media.upload_failed`, nothing leaks into a report) plus everything that doesn't touch S3. The **success** path (case 9) needs real S3: one test does it, guarded by `E2E_REAL_S3=1` (needs `aws sso login --profile mechanicpulse`). **Run by Akash 2026-11-02 against the real bucket: passed in mobile Chrome and mobile Safari** (30 passed, 6 skipped — with `E2E_REAL_S3=1` the three tests that need S3 to be *missing* skip themselves by design). Still untested: a real phone (camera, weak signal).
